# 門診背景刷新生命週期

本期以已驗證 `main` 的 `7161844509832e04f1edad670b526209b81fe542` 為基準，只整理主程式門診**背景掛號資料刷新**。F1–F12、照光劑量、醫療文字、會診寄信與打卡政策沒有變更。測試使用可注入的匿名假門診來源，沒有操作真實 HIS。

## 責任與依賴

| 元件 | 唯一責任 |
|---|---|
| `cmuh_common.outpatient_refresh_lifecycle.OutpatientRefreshLifecycle` | 持有請求去重、同類局部請求合併、先進先出佇列、單飛擁有權、900 秒逾時換代、完成／拒絕提交、停止與世代驗證。只依賴 Python 標準函式庫；不載入 `main`、`AutomationApp`、Tk、網路或醫院資料。 |
| `AutomationApp` | 保留自動／手動觸發、既有限流與刷新批次、可注入 `_appointment_fetcher`、現有 `BoundedThreadPoolExecutor`、快照政策、重啟安全閘門、UI 文字與 Tk 操作。工作緒只呼叫生命週期方法並把資料送入既有 UI 佇列。 |
| `UiClinicDataMessage`／`UiRefreshTickMessage` | 帶刷新世代；UI 消費端拒收舊世代的資料與進度。非刷新來源的 `None` 世代維持既有接收方式。 |

資料流：觸發者 → 生命週期搶佔或合併請求 → Tk 執行緒領取唯一待啟動工作 → 既有 executor 與假／正式可注入來源執行 → 來源把資料放進既有 UI 佇列 → Tk 消費該世代資料 → UI 確認完成並接力下一筆。背景緒不呼叫 `root.after`、`StringVar.set` 或按鈕操作。

## 生命週期與資源界限

- 同簽名的全量或局部請求只跑一次；同手動屬性的局部請求按醫師名稱合併。局部請求若已被等待中的集合涵蓋，就不再新增。佇列按「全量／局部 × 手動／自動」最多四類，單筆局部請求最多 256 位醫師；超限會記錄錯誤並在 UI 回報，不會擴大排隊工作。既有背景 executor 仍為 10 workers、`max_pending=60`，每批醫師的局部 pool 上限仍為 6。
- 逾時接管以單調時鐘量測 900 秒，只改生命週期的唯一世代；舊 worker 可自然返回，但不能清現任狀態、派送新批次或覆蓋新資料。節流中的進度 callback 也在寫入 UI 前核對世代。已完成的 worker 在其資料／進度訊息被 Tk 消費前仍保有世代；其他 UI 訊息的持續到達不會阻塞接力。
- 完成或拒絕提交只佔一個待處理槽；UI 消費端在同一控制物件中清理並接力。關閉時先停止控制物件、清除佇列與待處理槽並使世代失效，再關閉 executor；停止後的新請求與每醫師提交都不會派送。
- 提醒回查的背景啟動與生命週期停止操作互斥；已啟動的回查若在關閉或換代後才完成，也不再呼叫舊畫面的收尾函式。
- `reg52` 換代容量耗盡時仍只透過既有 `_restart_when_hotkey_idle` 安全閘門安排一次重啟，不在刷新模組內加入強制重啟。既有通知資格 `is_live_final`、快取 fallback、來源退避／限流、夜間頻率及前景保護皆沿用。
- 啟動優先批次 A 提早完成時，等待原定延遲的批次 B 提出請求並結束，才接續全量刷新；即使 B 的背景提交被拒絕，仍會嘗試全量刷新。若全量刷新已排隊並啟動，便清掉補跑旗標，避免後續局部刷新又觸發第二次全量查詢。
