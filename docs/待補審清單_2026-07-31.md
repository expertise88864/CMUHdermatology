# 第二段：CI 修復（base `13515d8`）

## 問題

CI 從 **run 293**（P2-07 加三道棘輪那一次）起**連紅四輪**，全部卡在 step 8
「skip 數量守衛」。而該步後面沒有 `always()`，所以**覆蓋率門檻與型別債棘輪
從來沒有在 CI 上執行過** —— 加了關卡卻沒確認它跑得起來。

根因：`CMUH_MAX_SKIPPED: "0"` 那個 0 是**推理**出來的，不是量出來的。當時只想到
`test_push_helper_antirevert` 有兩支在髒工作區才 skip、CI 的 checkout 永遠乾淨，
卻漏看同一個檔案裡還有一支是**平台條件** skip：`.gitattributes` 明訂
`*.py text eol=lf`，CI 的全新 checkout 一定是 LF，那支要求磁碟上是 CRLF，於是
永遠 skip。

## 改了什麼

1. **`check_skips.py` 從「數量上限」改成「宣告式期待」**（`skip_expectations.json`）。
   裸數字分不出「1 個合理的環境 skip」與「42 支被靜默關掉」—— 而紅燈時最順手的
   反應正是把數字調大，一調大兩者就都放行了。現在沒宣告過的 skip 理由一律紅，
   宣告過的超出上限也紅，且每條宣告**必須寫 why**（沒有 why 的條目直接判宣告檔無效）。
2. **關卡輸出改發 `::error::` annotation**。job log 要 repo admin 才下載得到，
   但 annotation 走 check-runs API 是公開可讀的 —— 這道關卡紅了四輪都看不出是
   哪幾支被 skip。三個關卡腳本都加。
3. **`ci.yml` 的三道棘輪都加 `if: always()`**，一輪拿到全部結果，不必「修一道、
   再等一趟」。
4. **CRLF 測試改成不看磁碟**：用 `git hash-object --path` 指定屬性查詢路徑，
   在任何平台都能餵 CRLF 進去問 git 會算成什麼 → 該支現在**永遠會跑**，
   順帶也守住 `.gitattributes` 的設定。

## 可疑處

1. `if: always()` 讓覆蓋率門檻在 pytest 紅掉時也跑，此時 `cov.json` 可能不存在。
   已改成「讀不到就說清楚是沒跑成、但一樣算失敗」，不過這條路徑只有單元測試涵蓋，
   沒有在真的 CI 失敗情境下驗過。
2. `skip_expectations.json` 目前只有一條（髒工作區）。**Tk 在 GitHub runner 上會
   不會 skip 我不知道**，刻意沒有先加一條 —— 預先宣告沒觀察過的東西就是重蹈
   「用推理設門檻」。若 CI 因此紅，annotation 會直接說出理由，屆時再判斷是環境
   還是測試被關掉。
3. `classify()` 用 `reason_contains` 子字串比對。理由字串若被改寫，宣告會失配 →
   紅（偏保守，可接受）；反之一個過短的 reason 可能誤蓋別的 skip，
   故加了選用的 `nodeid_contains` 收緊，並有測試釘住。

* `pytest -q` → **2632 passed, 2 skipped**（兩支都命中 `dirty-worktree` 宣告）

# 第三段：P2-03 型別化稽核事件（base `4030acf`）

外審原文：「稽核帳本用 denylist regex 消毒，應改為 typed audit events」。

## 舊做法錯在哪（三點，第一點是這次查到的實例）

`action_ledger.sanitize_text` 用兩條 regex（台灣身分證樣式、`\d{8,}`）猜哪一段像個資。

1. **猜不準，而且擋不住它宣稱要擋的東西。** F11 的 `_f11_read_course_value()` 讀療程欄
   **完全沒有把關**（只 strip + 全形轉半形），值直接進 `value=f"療程={course_value}"`。
   定位漂到姓名欄時，`王小明` 三個字對那兩條 regex 完全免疫，就這樣進了 append-only
   的 hash-chain 帳本。（測試 `test_a_patient_name_used_to_sail_through_the_old_regex`
   把「舊 regex 對它沒作用」也一起釘住，證明這不是假想。）
2. **誤遮無聲。** 醫令代碼今天最長 7 位；院方哪天發 8 位的，整欄集體變 `[REDACTED]`
   而沒有任何訊號 —— 偏偏那正是要查「改版把醫令寫錯」的時候。
3. **位置錯。** 消毒是在「已經拿到一段自由文字」之後才做。該問的是為什麼帳本會拿到
   自由文字。

## 改了什麼

新增 `src/cmuh_common/audit_events.py`：`Code` / `Measure` / `Observed` /
`Transition` / `Redacted` / `Reason`。帳本的 `value`/`detail` **只收這些型別**，
其他東西記成 violation 且**內容不落地**（`logging.error`，不是 debug）。
`sanitize_text` 與 `_PII_PATTERNS` 刪除。`SCHEMA_VERSION` 1→2（欄位由字串變 dict）。
main.py 全部 **21 個**呼叫點遷移。

* `Observed` 是唯一能描述「從 HIS 讀到什麼」的型別，而它**只存長度** —— 型別層面的
  「不記內容」，不靠註解提醒。
* `Reason` 是**封閉集合**，`detail` 再也塞不進自由文字。
* `Code` 是**字元集＋長度白名單**（不是樣式黑名單）。過不了時記的 violation 本身
  就是訊號：讀到的值不像代碼 ＝ 疑似定位漂移。

## 可疑處

1. **型別擋意外、不擋蓄意。** 有人硬要寫 `Code("chart", 病歷號)` 還是寫得進去。
   模組開頭有寫明這條邊界，請確認我沒有在別處把它說成更強的保證。
2. **呼叫端漏改的代價是「那一筆少了 value/detail」**（其餘欄位仍在）。這是刻意選的
   取捨。現存呼叫點由 AST 掃描釘住（`test_every_record_call_site_passes_typed_values`），
   但**新增**的呼叫點只有執行期的 `logging.error` 會抓到。
3. **`SCHEMA_VERSION` 2 與診間電腦上既有的 v1 紀錄混存。** `chain_hash`/`_canonical`
   是欄位無關的，所以驗證不受影響，有測試釘住（`test_v1_and_v2_records_verify_in_the_same_chain`）；
   但**查閱面**目前只有 `render()`，沒有 UI 消費 dict 形態的 value。
4. `_notify_audit_mismatch` 靠 `AuditValue.__str__` 產生告警信文字。若哪天有人拿掉
   `__str__`，信裡會變成物件 repr（有測試釘住，但那是間接依賴）。

## 順帶修掉/發現

* `audit_events.render()` 的一個真型別漏洞（`str | None` 回傳）—— 由型別債棘輪抓到。
* **未修、已另開待辦**：`_f11_read_course_value()` 那個沒把關的值同時也寫進
  `logging.info("讀到療程=%r")` → `automation_ui.log`。那個 log 是容量輪替、**沒有
  保存期限**，而且常整包交給開發者。帳本這側已修，log 那側是另一個改動。
