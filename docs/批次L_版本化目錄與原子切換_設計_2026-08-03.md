# 批次 L：版本化安裝目錄 + 原子切換（設計）

對應外部 review P1-01B / P1-01C。使用者 2026-08-02 定案「直接做版本化目錄 + 原子切換」。

**本文件是動工前的設計與回退路徑，尚未實作。** 第一次切換必須在診間電腦實地驗證過才算數 ——
這件事改的是「程式怎麼落地」，出錯的樣子是**全部六支程式都起不來**，不是某個功能壞掉。

---

## 1. 現在是怎麼做的

```
<app>\
  中國醫皮膚科主程式.pyw          ← Task Scheduler / 捷徑指的絕對路徑
  中國醫皮膚科打卡程式.pyw
  …（共 6 支 .pyw）
  src\…                          ← 128 個目標檔中的 107 個在這裡
  settings\…                     ← 設定與快取，不隨版本走
```

更新流程（`updater._commit_pending_writes`）：

1. Phase 1：每個檔的新內容先寫成各自的 `.upd.tmp`（含 fsync）
2. 交易日誌落地（`.updater_commit.journal`）
3. Phase 2：逐檔 `.bak` 備份 → `os.replace(.upd.tmp, target)` **就地覆蓋**
4. 任一步失敗 → 用 `.bak` 逐檔回滾；回滾也失敗就留著日誌等下次啟動重試

### 為什麼要改

- **就地覆蓋沒有「整批」的原子性。** Phase 2 逐檔換，中間死掉就是半新半舊。
  目前是靠 journal + `.bak` + 開機復原把它救回來 —— 能用，但那是**事後補救**，
  而且這一整個 session 的 F/K/K2 三批加上今天的 fsync 修正，全部都是在補這條路上的洞。
- **回滾要靠備份檔。** 備份不見了就真的回不去（`terminal`）。
- **更新中的視窗裡，程式是壞的。** 半新半舊的 `src/` 若剛好被啟動，行為未定義。

版本化目錄把這三件事一次消掉：新版**整套裝在旁邊**，裝好才切；切換是單一個原子動作；
回退不需要備份檔，把指標指回去就好。

## 2. 目標配置

```
<app>\
  中國醫皮膚科主程式.pyw          ← ★固定路徑、極薄的 stub★
  …（共 6 支）
  settings\…                      ← 不動，仍在 app 根目錄
  versions\
    2026.08.03.10\src\…           ← 一整棵 src
    2026.08.04.1\src\…
  current.txt                     ← 指標：一行版本字串
  src\…                           ← ★過渡期保留★（見 §5）
```

### 切換機制：指標檔，不是 junction

Windows 上可選的三種：

| 做法 | 原子性 | 需要權限 | 判定 |
|---|---|---|---|
| 目錄 junction（`mklink /J`） | ✗ 必須先刪再建，中間有空窗 | 要 | **不用** |
| 目錄改名 | ✗ 不能改到已存在的名字上 | 否 | **不用** |
| 指標檔 + `os.replace` | ✓ 同磁碟 rename 是原子的 | 否 | **採用** |

`current.txt` 只有一行版本字串。寫入走既有的 `atomic_io.atomic_write_json` 同款流程
（寫 tmp → **用可寫入 handle** fsync → `os.replace`）。

> 今天剛學到的：`open(p, "rb")` + `os.fsync` 在 Windows 一律回 EBADF，等於沒 fsync。
> 這裡一定要用 `rb+`。已抽成 `_fsync_path()`，並有涵蓋全 src 的 AST 守衛。

### stub 做什麼

```
讀 current.txt → 組出 versions\<ver>\src → 插到 sys.path 最前 → runpy 執行實際入口
```

在那之前先跑 `bootstrap_recovery`（批次 F 已經獨立出來、純 stdlib、不 import 任何本專案模組）。

## 3. 更新流程改成

1. 決定新版號 `V`，建 `versions\V.tmp\`
2. 把全部檔案裝進去（**全新目錄，不覆蓋任何正在被讀的檔**）
3. 逐檔驗 SHA256（manifest 已經有）→ 任一不符就整個丟掉，`current.txt` 動都不動
4. `os.replace(versions\V.tmp, versions\V)`：★這裡不能用★ —— 不能改名到已存在的目錄。
   改成直接裝進 `versions\V\`，裝完寫一個 `versions\V\.complete` 標記（原子）。
   沒有 `.complete` 的版本目錄一律視為半成品，開機時清掉。
5. **原子切換**：`current.txt` ← `V`
6. 清理：保留最近 N 個版本（預設 3），其餘刪除

失敗發生在第 5 步之前的任何地方 → `current.txt` 仍指舊版，**舊版一個位元組都沒被動過**。
不需要 `.bak`、不需要回滾、不需要 journal 重播。

---

## 4. 六支 `.pyw` 是唯一的單點

它們**也在 manifest 裡**（會被自動更新），而且是 Task Scheduler 指的固定路徑。
換句話說：**stub 壞掉不能靠切版本救回來** —— 那是唯一「切版本救不了」的檔案。

因此：

- stub 要**極薄且極穩**：只做「讀指標 → 設 sys.path → runpy」，不 import 專案模組、
  不碰網路、不碰 GUI。目標是寫完之後幾乎不再改。
- stub 的更新走**與其他檔不同的規則**：仍然就地覆蓋（沒有別的辦法），但
  **一定要先驗 SHA256、寫完立刻回讀比對**，不符就用 `.bak` 立刻復原。
- stub 自己要有**兜底**：`current.txt` 讀不到 / 版本目錄不存在 / 沒有 `.complete`
  → 退回舊的 `<app>\src`（過渡期保留，見 §5）。★退回要留下明確的 log 與一封信★，
  不可以安靜地跑舊版讓人以為更新成功了。

## 5. 遷移分三階段（每階段各自外審上線）

| 階段 | 做什麼 | 風險 | 回退 |
|---|---|---|---|
| **L1** | 只加 `versions\` 與 `current.txt` 的**讀取**能力：stub 先寫好，但 `current.txt` 不存在 → 走現行 `<app>\src`。更新流程完全不變。 | 低。行為與今天完全相同 | 還原 stub（`.bak` 就在旁邊） |
| **L2** | 更新流程改成裝進 `versions\V\` 並切 `current.txt`。**`<app>\src` 保留不刪**，當兜底。 | 中。第一次真正的切換 | 刪掉 `current.txt` → 立刻退回 `<app>\src`，一個動作 |
| **L3** | 觀察一至二週無事後，停止維護 `<app>\src`，改由保留 N 個舊版本目錄提供回退 | 低 | 指標指回上一版 |

**L2 的第一次切換要在診間電腦上人工驗證**：切換後六支程式各自啟動一次、確認版本號、
確認 settings 讀得到、確認排程觸發正常。這件事我沒辦法在這台開發機上代替你確認。

## 6. 失敗模式與方向選擇（每一條都要刻意）

| 情境 | 方向 | 理由 |
|---|---|---|
| `current.txt` 讀不到 | **退回舊 src 並告警** | 臨床程式必須起得來；但不可以安靜 |
| 指到的版本目錄不存在／沒有 `.complete` | **退回上一個有 `.complete` 的版本** | 同上 |
| 新版裝到一半斷電 | 下次開機清掉沒有 `.complete` 的目錄 | 半成品絕不可被指到 |
| SHA256 對不上 | 整個新版丟掉，指標不動 | 更新可以延後，跑到壞的版本不行 |
| 磁碟滿、裝不下新版 | 放棄這輪更新，指標不動，告警 | 同上 |
| stub 自己更新後回讀不符 | **立刻用 `.bak` 復原 stub** | 這是唯一救不回來的檔 |

方向的通則沿用這個 session 反覆確認過的那條：
**可修復性來自「舊版還在」，不是來自「不動手」。**

## 7. 需要你決定的兩件事

1. **保留幾個舊版本？** 預設 3（約 3× 的 src 體積，實測 src 樹不大）。
2. **L2 的第一次切換要挑哪台機器、什麼時段？** 建議挑一台非看診時段的機器先切，
   確認六支都正常再讓其他機器跟上。
