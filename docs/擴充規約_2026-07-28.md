## 1. 院方(HIS)改版 → 只改一支檔

**規約**

1. 使用者實機確認熱鍵還能不能用。
2. 只改 `src/cmuh_common/his_contract.py`:
   - `CALIBRATED_VERSION` 換成新版本;
   - 某個功能壞掉才改對應的 `MENU_ID_*`;
   - **`CALIBRATION_HISTORY` 最前面插一列,寫下憑據**(誰、怎麼確認的)。
3. `main.py` 只保留同名別名,**不得**再出現 `MENU_ID_xxx = 數字`。
4. 測試**不得**硬編碼版本字串,一律讀 `hc.CALIBRATED_VERSION` 組出來。

**由來**:2026-07-28 把校正版本從 1150720 改成 1150722,實際動到 **5 個檔** ——
版本常數在 `main.py:1502`、選單 id 在 2244 / 5096 / 5913(相隔數千行),另有 4 支
測試各自寫死 `"1150720"`。那不是「改一個常數」該有的成本,而且極易漏掉其中一處。

**為什麼憑據是規約的一部分**:選單 id 猜錯 = 熱鍵打到別的功能 = 寫錯病歷。
三次改版形態完全不同(2026-06-29 整批 +1、07-20 只有同意書 669→670、07-28 完全沒動),
**沒有規律可循,只能靠實機驗證**。歷史紀錄是為了讓下一個人知道這個數字憑什麼是這個數字。

**守門**:`tests/test_extensibility_primitives_2026_07_28.py`
(改版本沒補歷史 → `current_calibration()` 丟例外;main.py 又出現字面值宣告 → 測試紅)。

## 2. 新增一種「只通知一次」的告警 → 用 `AlertDeduper`

**規約**:`AlertDeduper("名稱")` + `send_once(key, send)`(同步)或
`claim(key)` / `release(key, ok)`(丟背景緒寄時)。**不要**再自己開
`notified` / `inflight` 集合與鎖。

`send` 必須回**真正的**成功與否 —— 不可用「沒丟例外」當成功
(SMTP 部分收件人被拒是正常返回,那種情況要能重試)。

**由來**:`main.py` 原本有四條互相獨立的告警路徑(稽核帳本健康、回讀不符、
HIS 改版偵測、止掛提醒無收件人),每一條都重寫同一套樣板,光模組級全域就有 8+ 個。
而這套樣板**很容易寫錯且錯了沒人發現**:

| 寫錯的方式 | 後果 |
|---|---|
| 忘了 inflight | 兩條緒各堆一條 60 秒逾時的寄信緒 |
| 先進 notified 再寄 | 一次 SMTP 故障 → 該告警**永久滅音**(codex P1 抓過) |
| 寄失敗不清 inflight | 該告警從此不再重試 |

**「告警永久失效」看起來跟「一切正常」一模一樣** —— 這正是不該靠每次重寫的東西。

**兩段式(claim/release)的存在理由**:佔用必須在 `spawn` **之前**同步完成,
否則兩次呼叫之間會各堆一條背景緒 —— 那正是 inflight 要防的事。

**已遷移**:稽核帳本健康、回讀不符。
**未遷移(下一輪候選)**:HIS 改版通知 —— 它多了「跨重啟去重的持久化 + 寄成功但寫檔
失敗要留待下次補寫」,有 8 個全域。`persist_probe` 參數已預留。**刻意不在同一批動**:
那條邏輯較複雜,而目前 Codex 外審額度用盡(2026-08-02 才回),沒有第二雙眼睛時
不做高風險重構。

## 3. 新增一個設定 → 只改預設宣告

**規約**

- 新增**設定鍵** → 加進 `cmuh_common/settings_defaults.py` 對應的 `DEFAULT_*` dict。
  載入(merge)、還原預設、摘要三件事自動涵蓋。
- 新增**設定檔** → 在 `SETTINGS_GROUPS` 加一個 `SettingsGroup`。
  設定頁的「還原預設設定」對話框會自動長出那一項,**不必改 UI 程式碼**。
- 新增**設定控件** → 把「從 `self.*` 灌回控件」那一行加進 `_reload_settings_into_ui`。

**⚠ 兩個一定要記得的坑**

1. **合併預設的順序**:`load_json_dict_ex` 的語意是 `base.update(file)`。若先把完整
   預設合進來,後面所有 `if key not in data` 的舊格式推導**全部失效** ——
   舊機器的檔案往往只有 `notify_dnd_*_hour`,勿擾時段會被悄悄換成預設。
   **先對原始檔案內容推導、最後才補預設。**
2. **「刻意清空」不可被預設復活**:使用者清空收件人時檔案裡是 `[]`(鍵存在),
   以檔案為準。同一個坑在 `smtp_mail` 的帳密快取踩過一次。

**由來**:預設值原本散在四處(`threshold_policy`、`app_settings` 的數個 `DEFAULT_*`、
`main.py` 中段的 `F8_QUICK_TEXT_DEFAULT`、UI 裡零星的 `.get(key, False)`),
新增一個設定要同時改四處且沒有一致性保證。

## 4. 從 HIS 畫面讀東西 → 用內容過濾,不要用 class 名稱

**規約**:識別控件用**內容特徵**(例如病人資訊橫幅同時要求「民國日期 + N診 + N號」),
不要只靠 class 名稱。找不到就**誠實回報找不到**,不要猜。

**由來**:`_find_disposition_memo` 早就是這套思路(寬鬆 class + 內容過濾);
`patient_locator` 沿用。改版時 class 名稱最容易整組失效,而內容特徵通常還在。

**★隱私邊界(不可退讓)★**

- 從畫面讀到的東西**拿得到 ≠ 該留**。一律**白名單**擷取,解析函式只回白名單 dict,
  呼叫端拿不到原文。
- `ALLOWED_FIELDS` 是機械性防線,新增欄位必須先進清單(有測試釘住 `name`/`birthday`
  不在其中)。
- **hash-chain 稽核帳本(`action_ledger`)不存病人明文識別**(2026-07-17 定案)。
  需要病人定位的資料走**獨立通道**(佇列的獨立欄位 + `settings/` 下的索引檔),
  不進帳本 `fields`。

## 5. 貫穿全域的四個病灶(每次動程式都先自問一次)

這四條是 2026-07 一整個月的 review 反覆抓到的**同一批根因**,不是抽象原則:

1. **讀檔/讀取失敗被當成「沒有資料」,然後被正常寫回覆蓋。**
   → 區分 `ok / missing / corrupt / error`;`error`(原檔完好、暫時讀不到)絕不可覆蓋。
2. **開迴路動作不回讀驗證 / 假成功。**
   → 「故障看起來跟正常一樣」是最貴的故障。`PostMessage` 成功 ≠ HIS 做了事。
3. **視窗/資源只用弱識別(class + title,沒有 PID / handle)。**
   → 能拿到 handle 就別靠 PID + 名稱猜(2026-07-27 隱藏桌面 systemftp 殘留的根因)。
4. **訊息陳述程式並不確知的事。**
   → 「已重建空 DB」在檔案根本沒搬走時是謊話;「已達門檻」在還沒檢查任何診次時是謊話。

**還有一條方法論**:清理/復原路徑**不可依賴正在耗盡的那個資源**。
孤兒清掃靠視窗列舉,而 `EnumWindows` 正是資源耗盡時最先壞的 —— 復原機制被它要修的
狀況弄壞了(2026-07-27 會診整早失效)。寫看門狗/自我修復前先問:
**這條路徑需要什麼?那個東西在故障當下還在嗎?**

## 6. 動「看起來少了防護」的程式碼之前

先查同區註解、`git log --grep`、既有測試名稱。**前人可能刻意不做。**

**由來**:2026-07-26 我加了「`#Gv_attppre` 表格不存在 = portal 改版」偵測,
但**完全相同的偵測在 2026-07-16(commit `d9f38be`)已經被撤回過** ——
空的 ASP.NET GridView 當日尚無刷卡時本來就不渲染 `<table>`,表格不存在**就是**
今天還沒打卡。把它當改版會在「早上未打卡」這個最該顯示的時刻變成「查詢失敗」。

反過來也成立:同一天我兩次說「找不到危害路徑,不做無憑據的改動」(OCR pitch、
updater 版本偏移),後來都被外審用具體反例推翻。
**「找不到」要當成「還沒讀夠」的訊號;「讀夠了發現前人刻意不做」才是結論。**
