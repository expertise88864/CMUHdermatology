## 可疑處與取捨（請重點檢視這幾條）

### 1. 用「閒置秒數倒退」偵測使用者回來，而不是設門檻值

閒置秒數在沒有新輸入時是**單調成長**的（每過一秒就多一秒），所以「比執行中的
峰值低超過容差」就是有人動了鍵盤或滑鼠。真的有輸入時是從 1800+ 秒直接掉回 0，
差距極大；容差 `2.0` 秒只用來吸收取樣抖動。

**可疑點**：如果 `GetLastInputInfo` 在某些情況下不是單調的（例如 session
切換、RDP 接管、GetTickCount 回繞邊界），這個判準會誤判成「使用者回來」而
不重開。誤判的方向是安全的（不重開），但會讓自動修復失效。

### 2. `elapsed` 必須讓機器重開 —— 這是刻意的

只守「該取消要取消」會把 fail-open 修成 fail-closed：自動修復**永遠不會發生**，
BDE 壞了就一直壞著。所以取消原因抽成 `_COUNTDOWN_ABORT_REASONS`，
**沒列在表裡的原因就是「讓它重開」**，並有一支測試專門斷言
`"elapsed" not in _COUNTDOWN_ABORT_REASONS`。

### 3. `idle_unknown` 取消重開

查不出閒置時間 → 保守當作可能有人在。代價是 `GetLastInputInfo` 若持續失敗，
自動修復就不會發生。這個方向與該檔案既有的
「查詢失敗回 0 ＝ 當作剛有輸入 ＝ 寧可不重開」一致。

### 4. `shutdown /a` 失敗只記 critical，沒有寄信

失敗代表「該取消卻取消不掉」，機器仍會重開。沒有加寄信的理由：機器距離重開
只剩約 50 秒，寄信執行緒不一定跑得完，而 log 是留得住的紀錄。
**這是取捨，不是遺漏** —— 若審查認為該補寄信（或改用同步短逾時寄送），可以提。

### 5. 改動了既有測試（請確認我沒有削弱它）

`tests/test_consult_persistent_session_2026_08_03.py::`
`test_recovery_during_countdown_aborts_the_shutdown` 原本是**掃原始碼字串**：
在 `_bde_reboot_watch_loop` 的原始碼裡找 `_bde_reboot_cancel.wait(timeout=55.0)`，
再檢查其後的文字。取消動作抽成函式後那個字串不在該函式裡了 —— 測試會
`ValueError` 而不是紅在「性質沒了」。**掃原始碼的守衛，程式碼一搬家就失效。**

改成直接驗它原本要的三個性質，搬到哪裡都測得到：

- 取消要用 `shutdown /a`
- 取消成功要回滾時間戳
- `/a` 失敗不得假裝取消了（時間戳也不可以被清掉）

# 批次 O：PID 檔改存可驗證身分（外審 P1-07）

## 問題

`src/cmuh_common/pidfile.py` 的 docstring 三處宣稱「PID 會被作業系統重用，不驗就
可能誤殺別人」，而實際驗證只有：

```python
proc.name().lower() in ("python.exe", "pythonw.exe", "python", "pythonw")
```

那只能濾掉**非 Python** 的行程。**這台機器上六支 CMUH 程式全都是 pythonw.exe**，
所以 stale PID 檔的 PID 被自家另一支程式重用時，驗證照樣通過。

而 `read_verified_pid` 的結果會走到
`watchdog_core._find_pids_holding_mutex` → `kill_pid` → `taskkill /F /T /PID`。
**這不是「找不到而不動作」，是強殺無關的自家程式連同它的整棵行程樹。**
宣稱擋住了，實際沒有。

## 修法

PID 檔改存 JSON：`schema` / `app_id` / `pid` / `create_time` / `executable`。

驗證分成兩級：

| 級別 | 欄位 | 不符時 |
| --- | --- | --- |
| 必要 | schema、app_id、pid 活著、**create_time 相符**、name 是 python 系 | 不採用 |
| 加強 | executable 路徑 | 讀得到才比；**讀不到不否決** |

核心是 **create_time**：被重用的 PID 必然屬於「後來才建立」的行程，建立時間不可能
與當初記下的相同。

## 為什麼是 create_time 而不是別的（實測，不是推理）

本機 397 個行程、非提權 Python：

| 屬性 | 成功 | 失敗 |
| --- | ---: | ---: |
| `create_time()` | 397 | **0** |
| `name()` | 397 | 0 |
| `exe()` | 396 | 1 |
| `cmdline()` | 393 | 4 |

`create_time()` 一次都沒失敗 —— 需要的判準剛好是最可靠的那個。
`cmdline()` 失敗 4 次，正好印證這個模組當初存在的理由。

## 請重點檢視的取捨

### 1. `exe()` 只做加強，讀不到不否決
實測會失敗（1/397）。若當成必要條件，就會在讀不到的機器上退回那條壞掉的 cmdline
路徑 —— **把這個功能修回它本來要解決的問題**。身分已由 pid + create_time 決定，
exe 是縱深防禦。**這是刻意的 fail-open，請確認我沒有開太大。**

### 2. 沒有加 nonce（外審有建議）
nonce 寫在檔案裡**無從與活著的行程對照**（讀不到別人的行程記憶體），不會增加任何
鑑別力。與其多一個看起來嚴謹、實際是裝飾的欄位，不如三個真的驗得到的檢查。

### 3. 舊格式（純數字）一律不採用
沒有 create_time，無從驗身分 → 退回 cmdline 路徑（＝這個模組出現以前的行為：
可能找不到，但不會殺錯）。程式下次啟動就自報成新格式，所以只是升級後到重啟前的
短暫狀態。**代價是這段期間半死救援失效**，有 log 說明。

### 4. 容差 `0.05` 秒
只是不想讓浮點表示的最後一位決定「要不要強殺一支程式」。真的被重用時兩者的建立
時間差好幾秒以上。兩個方向各有測試（開到極大＝重用偵測不到；歸零＝同一行程被誤判）。

## 改動既有測試（請確認我沒有削弱它）

`test_dead_pid_is_rejected` 與 `test_non_python_pid_is_rejected` 原本寫的是舊格式
純數字檔。新版把舊格式一律擋掉，於是這兩支會**因為錯的理由**通過 —— 名義上測
「行程已死」「不是 python」，實際只測到「舊格式被擋」。改用新格式 helper 寫檔，
讓它們真的走到各自宣稱的那條路。

- pytest：**3510 passed, 2 skipped**

# 批次 P（第一刀）：只能終止自己開的 systemftp（外審 P1-01）

## 問題

`our_pids` 來自【全機 PID 差集】：`(_systemftp_pids() - before) | {our_pid}`
（`src/consult_query.py` 兩處）。冷啟動最多等 120 秒，醫師在這段期間手動打開
住院系統，他那個行程就落進差集。之後：

```python
def _terminate_session_process(sess):
    """...不可能誤殺使用者的醫囑系統。"""   ← 宣稱
    close_pids(sess.our_pids)               ← 對【全機差集】送 WM_CLOSE
    ...TerminateProcess(sess.hproc)         ← 這半段才真的安全（靠 handle）
```

docstring 描述的是 handle 那半段，前面那行吃的是差集。**又是宣稱對不上實作。**

## 修法：分清楚兩件事

| | 判準 | 弄錯的後果 |
| --- | --- | --- |
| 找視窗的候選集 | 可以寬鬆（維持現狀，本刀不動） | 找不到 → 無傷害 |
| **可以終止的集合** | **必須封閉** | **關掉別人的程式** |

新增 `_verified_owned_pids(root_pid, candidates)`：只留 root 自己與可驗證的後代
（`psutil.Process(root).children(recursive=True)`）。終止端改用它。

另外 SW_HIDE 後備模式原本 `subprocess.Popen(...)` **把物件整個丟掉**，那條路因此
沒有任何直接的所有權事實 —— 與 2026-07-27 事故同一條教訓（spawn 要留 handle）。
改成留住並以其 pid 當 root。

## 請重點檢視的取捨

### 1. 驗不出後代時只認 root（可能留孤兒）
root 已結束、或 psutil 不可用時，只終止 root。代價是它的後代可能變孤兒；但孤兒
有既有清理機制（`_kill_systemftp` 的 before 快照），而**關掉醫師的 HIS 沒有任何
補救**。★寧可留孤兒，不可誤關★ —— 請確認這個方向沒有被我開得太寬。

### 2. `borrowed` 開關本來就不足以封閉所有權
它只擋「啟動前就存在」的行程。醫師在冷啟動那 120 秒內**新開**的不在 `before`
裡，borrowed=False，舊邏輯照樣會關掉它。`before` 快照只認得「更早以前」。

### 3. 本刀【沒有】改的部分（刻意）
- `our_pids` 本身仍是差集（找視窗用），沒有換成 process tree
- P1-02 的「找不到屬於自己的登入視窗就中止、不借用」**尚未做**

理由：我無法在開發機上確認 systemftp 的真實行程拓撲（登入視窗的 PID 究竟是
`_spawned_pid` 本身、它的後代、還是由服務另外生出來的兄弟行程）。若拓撲假設錯
而我把找視窗那側也改成只認 process tree，會讓冷啟動在診間機器上**完全找不到
登入視窗**。所以這一刀只封閉「終止」這個會造成傷害的方向，並加上實機證據 log：

> `[session] 收尾時排除 N 個不屬於本次啟動的 systemftp(pid=[...])`

那行出現就代表差集確實含有不屬於我們的行程 —— 是把找視窗那側也收緊的依據。
只記 PID 與數量，不記視窗標題（非病人資料）。

# 批次 Q（第一刀）：會診識別改成 request-level（外審 P1-04）

## 問題
`_consult_signature_from_roster()` 回傳【病歷號集合】。它只能回答「這位病人在不在
清單上」，回答不了「這是不是同一位病人的**另一張**會診」——因為
`{"12345678", "12345678"} == {"12345678"}`。同一病人的第二張會診被吸收掉 →
★漏寄★，臨床上最糟的方向。

## 修法
識別改成 `病歷號|日期|時間`（`_consult_id_from_row`）。缺日期/時間時退回只用病歷號
（＝舊行為），鑑別力只會變好或持平。

### ★不採納外審建議把病房/床號放進識別★
審查建議 `chart + 會診時間 + ward/bed + 申請科別`。**病房/床號不採納**：病人轉床
很常見，而轉床**不是新的會診** —— 放進識別會在每次轉床多寄一封（誤寄）。真正屬於
「這張會診單」的是**申請時間**：轉床時不變，新開一張時必然不同。有測試守這一條。

## ★升級相容：最危險的地方★
舊基準 `consult_notified.json` 只有 `charts`（病歷號）。若拿新識別直接對它做集合
相減，**升級當下每一張既有會診都會變成「新的」→ 對團隊整份重寄**。

作法：
- 讀到沒有 `ids` 的舊檔 → 記 `_notified_is_legacy=True`
- `_new_consult_ids()` 在 legacy 時降級成**病歷號粒度**比對一輪
- `_save_notified()` 一寫就是新格式，旗標關掉，之後恢復完整鑑別力
- **檔案同時保留 `charts`**：診間電腦不是同時更新的，新版寫的檔可能被還沒更新的
  舊版讀到；舊版只認得 `charts`，少了它會整份重寄

## 我自己改壞又被既有測試抓回來的地方

- 還沒載入 → 空清單被當成「成功且真的沒有病人」→ 基準被剪成空
  → 下一輪所有既有會診都變「新」→ **對團隊重寄整份清單**
- 載入到一半 → partial roster 被存成基準 → 還沒出現的病人此後不算新 → **漏寄**

**固定睡多久都治不了**（慢的機器仍會失手）。要看的是「內容有沒有還在變」。

## 修法
`_await_stable_roster()`：連續 3 次讀到完全相同才算穩定（每 0.25 秒取樣，逾時 6 秒）。

**空清單也要通過同一道關**：「找不到 radio」與「真的沒有病人」在畫面上長得一模
一樣，唯一分得出來的線索就是它穩不穩定。

## 為什麼不做 `RosterSnapshot` 全套狀態機
外審建議 VALID_NONEMPTY / VALID_EMPTY / LOADING / UNSTABLE / SCHEMA_INVALID /
TIMEOUT 六態，以及「空清單必須有明確的 UI marker」。

**那個 marker 我不知道長什麼樣** —— 那是實機知識，開發機上沒有 HIS 可以量。
批次 P 已經因為同一個理由留手過一次；憑猜測寫一個 marker 判定，猜錯就是把
「真的沒病人」也判成 LOADING，每輪 fail-open 寄信 = 天天洗信箱。

所以這一刀只做**穩定性**這個不需要實機知識的判準，而且**接上既有通道**：
不穩定 → `roster_texts = None` → 走既有的「無法判斷 → fail-open 照寄、
**不更新基準**」那條路。呼叫端一行都不用改。

顯示用與判斷用分開：看到什麼照樣附在信裡，但「有沒有新會診」不拿一份還在變的
清單去判斷。

## ★P1-05：teardown 關不掉真正的 HIS —— 這是我造成的迴歸★

# P1-06：移除全機 PID 差集的 `taskkill`（外審第 3 輪）

## 問題
`_kill_systemftp(before_pids)` 算出 `目前 systemftp PID − 任務開始前快照`，對整個
差集執行 `taskkill /F`。**它完全繞過這幾輪建立的 ownership 驗證。**

「任務期間新出現」不等於「是我們的」——醫師在本次任務**執行中**手動開的住院系統
也不在 before 快照裡。而它會在任何可重試錯誤前執行，**包括寄信失敗**：

```
會診查完 → 醫師手動開 HIS → SMTP timeout → 醫師的 HIS 被 taskkill /F
```

函式自己的舊 docstring 也承認了這個窄窗（「使用者若『恰好在本任務進行中』才手動開
systemftp，會被納入」）。

## 修法
改成收掉**我們自己的 session**（`_session_close` → `_close_session_windows`：對確切
主畫面送 `WM_CLOSE` 並回讀確認），差集只留作證據 log。

`consult_query.py` 內的 `taskkill` 呼叫**歸零**。

### 為什麼不保留一份「僅供對照」的舊實作
我原本留了 `_kill_systemftp_DISABLED`，隨即刪掉 —— 那等於在程式碼裡留一把上膛的槍，
日後有人誤呼叫就回到原樣。git 歷史已經留著原版。

### 取捨（請檢視）
真的清不掉時，下一次 attempt 可能撞上院方「最多兩個」上限而**明確失敗**。
這是刻意的：**前者看得見、修得了；後者醫師只會看到自己的系統忽然消失。**
孤兒會不會累積，靠新增的證據 log 觀察。

## 改動既有測試
`test_kill_systemftp_only_new_orphans` 原本斷言「只殺任務期間新增的」。它守的性質是
「絕不碰任務前就存在的實例」——現在守得更強：**什麼都不殺**。已改寫並在 docstring
說明原本斷言什麼、為什麼那個判準不夠。
