# 深度穩定性+資源優化工單(2026-08-26 定稿)

## 背景(使用者 2026-08-25)
會診查詢+打卡改在★治療室電腦★常駐(共用、隨時有人使用;原本在閒置電腦)。
「不能太消耗資源導致電腦跑其他程式太慢」是硬約束。工單涵蓋三支:
會診查詢 / 打卡 / 主程式(主程式跑診間電腦,以穩定性為主)。

## 原則
1. ★先量測再改★:憑感覺調頻率/砍功能,量不到改善也量不到退化。
2. 每一批照既有管線(實作→四關→突變→外審 APPROVE→push_helper)。
3. ★守衛/優化不可自帶新失效模式★(降優先權不能讓自動化逾時誤判成故障)。

## Phase 1:資源(便宜大改善)
* 兩支常駐程式自降 BELOW_NORMAL_PRIORITY_CLASS(★不用 Windows「背景模式」
  PROCESS_MODE_BACKGROUND_BEGIN —— 它會把 IO/記憶體優先權壓到最低,
  自動化等待逾時會被餓出假故障★)。
* ★子行程會繼承優先權★(Codex,採納;CreateProcess 文件明定):Python 降了
  之後,spawn 的 Chrome/systemftp 會跟著 BELOW_NORMAL —— 而它們是工作本體。
  所以【建立子行程前】與【時間敏感的自動化區段】要暫升 NORMAL,
  ★finally 恢復★(恢復失敗要有告警,不能靜默留在 NORMAL)。
* Chrome 已查證:headless=False 只在人工「測試登入」流程,常駐池無缺口;
  共用旗標已停用 extensions/圖片/背景網路(chrome_options.py)→ 此項無工作。
* IMAP 輪詢:★每 tick 開兩條新 TLS/IMAP 連線★(觸發信掃描+遠端指令掃描,
  非長連線)。★使用者 2026-08-26 定案:20s→60s★(連線數 -67%;觸發平均
  等待 10s→30s、最差 20s→60s;排程寄信 12:31/17:01 不受影響)。
* 待量測證據決定的:截圖/擷取流程的頻寬、log IO。
