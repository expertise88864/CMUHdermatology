**1. 同一輪多位病人完成時,間隔只有第一位拿到(高估平均看診時間)**

`newly_completed = current_completed_set - tracker['last_completed_set']` 是**集合**,
門診動態輪詢間隔 `CLINIC_LIGHT_REFRESH_SECONDS = 60` 秒,同一輪出現 2 位以上完成是常態。
原本的迴圈逐筆算 `doctor_pace = current_timestamp - tracker['last_valid_completion_time']`,
而且**在迴圈內**就把 `last_valid_completion_time` 更新成 `current_timestamp` →
集合迭代到的第一位拿到完整 300 秒,同批其餘拿到 0。

那些 0 會被 `duration_stats` 的中位數帶裁掉(所以平均不會直接歸零),但結果是
「兩人共用 300 秒」被記成**一筆 300** 而不是**兩筆 150** → 平均看診時間、
以及用它乘上候診人數的「預估剩餘」被系統性高估。

同一段還有第二個問題:`first_valid_skipped` 只跳過集合迭代到的第一位 ——
同批其餘拿著**同一個無效基準**算出的 0 照樣進了樣本。基準無效就該整批跳過。

修法:抽成 `clinic_state.apply_newly_completed(tracker, newly_completed, ts)`
純函式(與該檔既有的 `new_clinic_tracker` / `restore_tracker_from_state` 同層級),
先分類照光/有效,再把同一段間隔**平分**給整批有效完成;`first_valid_skipped`
未設時整批不取樣;`< 3600` 的休息/斷線門檻語意維持不變(對整段原始間隔判定)。

**2. `platform_win._admin_relaunch_params` 在 .exe 模式會把自己的路徑當引數傳給自己**

`run_as_admin` 用 `ShellExecuteW(None, "runas", sys.executable, params, ...)`,
params 原本是 `list2cmdline(sys.argv)` —— frozen(PyInstaller)模式下 `sys.executable`
就是程式本身、`argv[0]` 也是同一個 exe,於是變成
`app.exe "C:\...\app.exe" --background`。
同套件的 `paths.restart_self` 早就分兩種模式處理(frozen 時 `[sys.executable] + args`),
這裡沿用同一條規則。

⚠ **補審時請特別看這一項**:目前 repo 沒有 `.spec` 也沒有打包腳本,實務上跑 `.pyw`,
所以這是「與既有模式對齊的一致性修正」而非實機故障。若外審認為不該動提權路徑,可以撤回。

### 週五值班↔週六切片連動 + 班數平衡權重提升

| 檔案 | 變更 |

**使用者需求(2026-07-27 原話)**

1. 「若R排班 盡量禮拜六早上切片的人 也同樣安排禮拜五值班,但是要在排班允許的
   情況下(最後條件,可以選擇的話盡量禮拜六早上切片的人選也值班禮拜五)」
2. 「原本設定就是盡量值班那周六日的人要切片(R2/R3) 若是R1值班則是安排R2/R3值班,
   但是R2/R3週六切片次數要平均分配 盡量讓R2/R3一整年下來週六切片次數一樣」
3. 「在R/VS值班, 若點數允許的情況下, 也盡量要安排班數接近或一致」

第 2 點查證後**既有實作已完全滿足**(值班連動 → 否則次數平衡,`counts` 永久累計
於 `biopsy.json`,`rollback_biopsy`/`settle_biopsy` 同月重排不重複計)。未改動,
只補了一支 12 個月的迴歸測試釘住「全年全距 ≤1」。

**做了什麼**

切片人選有兩種來路,所以連動要兩側各做一半:
- **值班側** `FridayBiopsyLinkRule`(新):週六排到 R2/R3 時(→ 值班連動使他成為
  切片者),獎勵同一人也值週五。
- **切片側** `assign_saturday_biopsy`:週六值班是 R1 → 走次數平衡,此時
  **次數平手**才優先挑已值週五者(取代原本的「與上次不同者優先」輪替;
  輪替本來就只是次數平衡的弱化版,全距仍由 `run` 保證 ≤1)。

**權重帶(這是最需要外審看的部分)**

```
點數公平            10,000 / 0.01 點        ← 絕對優先,以下全部加起來都不該超過
5 連值           10,000,000
4 連值            3,000,000
週末上限 >2       ~4-10 點級(動態)
─────────────────────────────────────
班數全距 1 單位        1,500   ← 由 1 提升(原本連 3 連值罰則都輸,幾乎不生效)
週五連動 1 個            600
3 連值 1 扇窗            500
```

- 用**獎勵連上**而非**懲罰沒連上**:後者會讓求解器改把 R1 排進週六來躲罰則
  (成本 0),反而破壞使用者更想要的「週末由 R2/R3 值」。
- ⚠ **誠實揭露的取捨**:每月最多 5 個週六 → 連動總獎勵上限 3,000 > 班數全距
  1 單位 1,500,亦即「3 個以上的週五連動」可以換掉 1 天的班數差距。
  要完全支配需 `RANGE_WEIGHT > 3,000`,但那會讓班數項在全距較大時突破點數
  步進,反而危及最高優先的點數公平。取捨後選擇「單一連動絕不換班數」。
  **若外審或使用者認為這個取捨不對,改 `RANGE_WEIGHT` / `LINK_WEIGHT` 即可,
  兩個常數都有測試釘住相對大小。**
- ⚠ **班數平衡權重 1 → 1500 是行為變更**:它現在也壓過 3 連值罰則(500)。
  依據是使用者第 3 點把班數一致列為明確要求,而 2026-07-13 已定案
  「3 天勉強可接受」。實測 2026/8 基準情境下解不變(班數 10/10/11、
  點數 13/14/14、週末 2/4/4 全部相同)。
