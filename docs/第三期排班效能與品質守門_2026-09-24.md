# 第三期：排班效能與品質守門

基準是第二期正式 `main` 的 `94318b3da5062ea96023d57f028c898c9b65edea`。本期只使用完全合成的日班表；量測沒有讀取正式排班儲存、病人資料、HIS、郵件或打卡網站。前兩期既有的背景求解、取消、嚴格快照、過期結果拒絕、現況統計及舊 benchmark 均沿用。

## 比較方法

`scripts/benchmark_day_roster.py` 記錄每次求解、每一層的狀態、目標值、最佳界限、模型大小與耗時；另核對必要照光／治療室、週三下午例外、重複排班、請假、家醫可參與時段、鎖定格與診間容量。品質摘要從實際結果計算 PGY 照光、週三下午、治療室、跟診、必要工作與總量；Clerk 整梯與跨月配額；家醫／外訓可參與半日、跟診比例與半月切片；每人每日／每週跟診與已知門診醫師分布；並保留警告全文。手動照光偏移及假日也有專屬合成案例。

`scripts/compare_day_roster.py` 在兩個 checkout 的獨立 Python 行程中執行相同案例；每邊先暖機一次，正式配對輪流採基準→候選、候選→基準的順序。工具核對 Python、平台、CPU 核心數、OR-Tools、輸入指紋、工作樹內排班與 benchmark 原始碼是否乾淨；少於每版十筆的試跑只供篩選，不可稱為採納證據。完整結果 JSON 存於工作區外。

品質閘門先拒絕任何硬限制問題、候選層缺失、層狀態或已取得目標值變差。較高優先層真正改善時，容許不同排法，但 Clerk／家醫／外訓／PGY 的最低需求、課程上限、PGY 工作量差與個人可跟診的醫師種類不得退步；每日、每週、醫師次數、警告與每層界限仍逐筆列出供審查。最佳界限下降不一律是退步：當較小的目標值已證明最優時，新的界限也會下降。工具保守地要求其餘沒有優先層收益的結果保持完整品質摘要一致。

速度採納門檻預先固定為：兩個多人 Clerk 重點案例中，至少一個中位數改善 8% 且十組配對至少八組候選較快；另一個重點案例中位數不得慢超過 3%；其餘案例中位數不得慢超過 10% 或 0.1 秒（取較寬的自然波動容忍）。15% 是期待幅度，並非可犧牲品質換取的硬目標。十筆樣本不足以估計可靠 p95，故只報中位數、範圍與配對勝出數。

## 分開進行的三項實驗

| 實驗 | 假設 | 短測觀察 | 決定 |
|---|---|---|---|
| 1. 收緊跟診前綴偏差變數上界 | 每人每日最多兩個跟診時段，`n` 天第 `i` 個前綴的偏差上界可證為 `2*i*(n-i)`；縮小等價整數域可能減少搜尋 | 兩個重點案例各兩筆：4 Clerk 中位數約快 3%，5 Clerk＋家醫／外訓約快 12%；排班品質摘要相同 | 尚未採納；效果較小，短測含電腦負載波動 |
| 2. 把前一層最優排法提示給下一層 | 既有排法在加上該層最優等式後仍可行，作為非強制搜尋提示可能讓下一層更快找到好解 | 兩個重點案例各兩筆：分別約快 52% 與 28%；4 Clerk 案例 PGY 總工作量更平均，混合案例由跟診層 `UNKNOWN` 進到最後一層 `OPTIMAL` | 繼續正式比較；不同排法依優先層及每人最低需求審查 |
| 3. 調整求解器線性化層級 | 搜尋成本可能下降 | 雖較快，混合案例的最低需求層目標值及求解狀態明顯變差，後續層未執行 | 淘汰；不可把較快當成品質改善 |
