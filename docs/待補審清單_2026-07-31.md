# 第二段：CI 修復（base `13515d8`）

## 問題

CI 從 **run 293**（P2-07 加三道棘輪那一次）起**連紅四輪**，全部卡在 step 8
「skip 數量守衛」。而該步後面沒有 `always()`，所以**覆蓋率門檻與型別債棘輪
從來沒有在 CI 上執行過** —— 加了關卡卻沒確認它跑得起來。

根因：`CMUH_MAX_SKIPPED: "0"` 那個 0 是**推理**出來的，不是量出來的。當時只想到
`test_push_helper_antirevert` 有兩支在髒工作區才 skip、CI 的 checkout 永遠乾淨，
卻漏看同一個檔案裡還有一支是**平台條件** skip：`.gitattributes` 明訂
`*.py text eol=lf`，CI 的全新 checkout 一定是 LF，那支要求磁碟上是 CRLF，於是
永遠 skip。

## 改了什麼

1. **`check_skips.py` 從「數量上限」改成「宣告式期待」**（`skip_expectations.json`）。
   裸數字分不出「1 個合理的環境 skip」與「42 支被靜默關掉」—— 而紅燈時最順手的
   反應正是把數字調大，一調大兩者就都放行了。現在沒宣告過的 skip 理由一律紅，
   宣告過的超出上限也紅，且每條宣告**必須寫 why**（沒有 why 的條目直接判宣告檔無效）。
2. **關卡輸出改發 `::error::` annotation**。job log 要 repo admin 才下載得到，
   但 annotation 走 check-runs API 是公開可讀的 —— 這道關卡紅了四輪都看不出是
   哪幾支被 skip。三個關卡腳本都加。
3. **`ci.yml` 的三道棘輪都加 `if: always()`**，一輪拿到全部結果，不必「修一道、
   再等一趟」。
4. **CRLF 測試改成不看磁碟**：用 `git hash-object --path` 指定屬性查詢路徑，
   在任何平台都能餵 CRLF 進去問 git 會算成什麼 → 該支現在**永遠會跑**，
   順帶也守住 `.gitattributes` 的設定。

## 可疑處

1. `if: always()` 讓覆蓋率門檻在 pytest 紅掉時也跑，此時 `cov.json` 可能不存在。
   已改成「讀不到就說清楚是沒跑成、但一樣算失敗」，不過這條路徑只有單元測試涵蓋，
   沒有在真的 CI 失敗情境下驗過。
2. `skip_expectations.json` 目前只有一條（髒工作區）。**Tk 在 GitHub runner 上會
   不會 skip 我不知道**，刻意沒有先加一條 —— 預先宣告沒觀察過的東西就是重蹈
   「用推理設門檻」。若 CI 因此紅，annotation 會直接說出理由，屆時再判斷是環境
   還是測試被關掉。
3. `classify()` 用 `reason_contains` 子字串比對。理由字串若被改寫，宣告會失配 →
   紅（偏保守，可接受）；反之一個過短的 reason 可能誤蓋別的 skip，
   故加了選用的 `nodeid_contains` 收緊，並有測試釘住。

* `pyright` → 0 errors, 0 warnings
* `pytest -q` → **2632 passed, 2 skipped**（兩支都命中 `dirty-worktree` 宣告）

# 第六段：黑螢幕改按鈕觸發 + 捷徑按鈕對齊（base = 第五段）

## 1. 黑螢幕改成設定頁的按鈕（並刪除自動關螢幕）

使用者原話：「在設定頁面做一個按鈕，按下後讓黑色畫面直接覆蓋著螢幕及副螢幕、
包括系統列…若有偵測到有滑鼠的移動或是鍵盤的輸入就馬上恢復原狀，然後刪除原本
15 分鐘進入螢幕關閉的模式」。追問後定案：**兩層都刪，螢幕只由按鈕控制**。

刪掉的兩層：
* `powercfg /change monitor-timeout-ac/dc 15` —— 從電源計畫拿掉（睡眠/休眠停用保留，
  函式改名 `_apply_screen_off_power_plan` → `_apply_never_sleep_power_plan`，
  因為舊名已經不描述它在做什麼）。
* 閒置 15 分鐘的 watchdog：`_force_screen_off_watchdog` / `_screen_off_due` /
  `_send_monitor_off` / `_log_display_power_requests` / `_request_blackout`
  與相關常數全部刪除，開緒點也拿掉。

新增：設定頁「螢幕」區塊的「立即黑螢幕」按鈕 → `AutomationApp._blackout_now()`。

★**這一段最需要外審看的設計**：待命（arming）★
按鈕是用滑鼠按的，所以黑幕出現的瞬間 `GetLastInputInfo` 的閒置是 0、游標又停在
黑幕上隨時送 `<Motion>` —— 沒有待命期的話黑幕會被自己的開啟動作立刻收掉，
按鈕等於完全沒用。所以加了 `ARM_IDLE_SEC` / `ARM_MAX_SEC`：
使用者放手（idle 跨過門檻）或超過硬上限 4 秒才進入待命，待命之後**規則一字未改**
（任何輸入馬上收，不分滑鼠鍵盤、不問幾 px）。

★這不是使用者否決過的那個 25px 飄移門檻★ —— 那是「什麼算輸入」的門檻，
這是「從什麼時候開始算」。程式碼與測試都寫明這個區別。

**做這段時抓到自己一個真 bug**：第一版 `ARM_IDLE_SEC = 0.8` 小於
`INPUT_FRESH_SEC = 2.0`，同一輪輪詢會先待命再馬上收，而且輪詢間隔只有 250ms、
閒置時間不可能從 <0.8 跳到 ≥2.0 → **黑幕永遠留不住，按鈕永遠沒用**。
已改成 `ARM_IDLE_SEC = INPUT_FRESH_SEC` 並加測試釘住這個不等式，
另加一支端到端測試（按下→放手→留著→回來碰→收起）。

## 2. 「院內系統捷徑」左右按鈕高度沒對齊

* 左邊 `sticky="nw"` 容器 + 內部 `pack(pady=1)`；右邊 `sticky="nsew"` 容器 +

  隨字體縮放而變。

改法：左右兩排改成**共用 `links_frame` 的同兩列**，值班資訊移到自己的欄；

1. **黑幕的「蓋住工作列」沒有實機驗證**。靠的是 `overrideredirect(True)` +

2. **待命期間黑幕是「收不掉」的**（最長 4 秒）。這是診間機，我認為 4 秒的硬上限

4. 順手修了 P3-01 掃描器的一個洞：`.claude/worktrees/` 底下有 spawned agent 開的

# 第七段：黑幕改「一個螢幕一片」（base = 第六段）

★使用者實機回報★：按下按鈕後「只有副螢幕跟主螢幕 1/3 有黑屏，其他都沒有」。

## 兩個獨立的成因

原本是**一個**視窗蓋整個虛擬桌面（`GetSystemMetrics(SM_*VIRTUALSCREEN)`）：

1. **Tk 的 `wm maxsize` 預設是【主螢幕】大小** —— 超過就被夾掉。而「虛擬桌面比
   主螢幕寬」正是雙螢幕的常態，所以那個視窗本來就會被截短。
2. **本程式刻意是 system-DPI-aware**（見 `platform_win.set_dpi_awareness`：Tk 不處理
   `WM_DPICHANGED`，per-monitor 模式下視窗搬到不同 DPI 的副螢幕版面會破）。
   兩台螢幕縮放比例不同時，Windows 會對「與系統 DPI 不同」的那台做座標虛擬化 ——
   用一個涵蓋全部的矩形去算，位置與大小就會對不上。

## 改法

`monitor_rects()`：用 repo 既有的 `get_active_physical_monitors()`（會排除鏡像顯示
驅動）逐一列出實體螢幕，**每台螢幕開一個黑幕視窗**。單片不超過所在螢幕 → 夾不到，
也不必跨越不同 DPI 的邊界。另外仍明確 `win.maxsize(w, h)` 解除上限（副螢幕比主螢幕
大時單片也會踩到）。列舉不到時退回原本的單一虛擬桌面矩形，**絕不回空清單**
（空清單等於沒有黑幕）。

`_win`/`_hwnd` → `_wins`/`_hwnds`；`active` 與 `active_from_any_thread` 改成
「**任一片還蓋著就算黑幕還在**」（偏保守：剩一片沒收掉時仍要擋熱鍵，否則那一下按鍵
會打在使用者看不見的畫面後面）。`_destroy` 逐片各自 try —— 一片失敗不可以讓其餘
留在螢幕上。新增 `panel_count`（回讀，不是旗標）。

`show()` 現在會 log **要求的矩形與回讀到的實際幾何**：使用者再回報「蓋不滿」時，
這是唯一能分辨「算錯了」與「算對但被夾掉」的資料。

## 可疑處

1. ★**這次仍然沒有實機驗證**★。測試用注入的矩形，量不到真實的 DPI 虛擬化與
   z-order（工作列有沒有被蓋住）。上面兩個成因是從症狀 + 程式碼推出來的，
   **不是量出來的** —— 新加的 log 就是為了下一次能用資料判斷。
2. 多個 topmost `overrideredirect` 視窗的 z-order 沒有明確控制（只有第一片
   `focus_force`）。工作列所在的那台螢幕若不是第一片，理論上可能蓋不過工作列。
3. `panel_count`/`active` 用「任一片」而不是「全部」：若某片建立成功但沒 mapped，
   `show()` 會回 True 而實際少蓋一台。目前沒有「每片都要 mapped」的檢查。

## 本機驗證

* `ruff` → All checks passed；`pyright` → 0 errors, 0 warnings
* `pytest -q` → **2734 passed, 2 skipped**（黑幕再 +6：一螢幕一片、大於主螢幕不被夾、
  整組收、只剩一片仍擋熱鍵、列舉失敗的兩條退路）
* 三道棘輪全過（shared 74.2%、total 50.2%）

# 第八段：黑幕改用 Win32 擺 + 回讀驗證（base = 第七段）

★使用者第二次實機回報★：「現在變成主螢幕有黑 但是副螢幕沒有黑 或是只黑三分之一」。

## 診斷

第七段改成逐螢幕之後，主螢幕對了、副螢幕還是 1/3 —— **那個比例就是縮放比**。
螢幕矩形是 `GetMonitorInfo` 給的（Win32 座標空間），視窗卻是用 Tk 的 `wm geometry`
擺的；本程式是 system-DPI-aware，兩台螢幕縮放不同時**這兩者不是同一個座標空間**。

## 改法

* **查與擺走同一個 API**：建立視窗後用 `SetWindowPos(hwnd, HWND_TOPMOST, x, y, w, h,
  SWP_NOACTIVATE|SWP_SHOWWINDOW)` 把它校正到 Win32 座標。
* **擺完回讀**：`GetWindowRect` 讀回實際矩形與要求比對，不一致就記 warning 並把
  **兩組數字都寫出來**。`SetWindowPos` 回 True 只代表呼叫成功 ——
  「送出去就當成功」正是這個 repo 反覆出事的形狀（SC_MONITORPOWER 也是這樣）。
* 校正失敗（例外）時退回 Tk 的擺法並留 warning：蓋一部分遠優於完全沒有黑幕。
* 新增 `panel_rects()`（Win32 回讀，不是 Tk 的 `winfo_*` —— 兩者在多螢幕不同縮放時
  會給出不同答案，而使用者看到的是 Win32 那個）。

## 可疑處

1. ★**這是第三次靠推理修同一個症狀**★。前兩次都沒改對。這次的差別是：
   即使推理又錯了，**回讀會把它講出來**（log 有要求與實際兩組數字），
   不必再猜第四次。這一點請外審重點確認 —— 回讀路徑本身有沒有可能靜默失效。
2. `SetWindowPos` 與 `GetMonitorInfo` 對同一個行程是否保證同一座標空間，
   我是**依 Win32 的 per-process DPI 虛擬化語意推斷**的，沒有在多縮放環境實測。
3. 工作列 z-order 仍未驗證（第七段的可疑處 2 未解）。

* `ruff` → All checks passed；`pyright` → 0 errors, 0 warnings
* `pytest -q` → **2739 passed, 2 skipped**（黑幕再 +5：Win32 擺法、回讀一致、
  蓋不滿要有兩組數字、回讀失敗要說、校正失敗不可退化成沒有黑幕）
* 本機（單螢幕）實測 `panel_rects()` 回讀值等於要求值
