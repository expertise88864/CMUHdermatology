# P2-06：main.py 分層施工計畫

外審原文：「main.py 約 17,000 行，缺乏分層」。這是**多週**的工作，不可能一次做完，
所以先把它切成可以獨立上線、獨立回滾的刀。本檔記錄**量出來的現況**與切法，
接手的人從「下一刀」往下做即可。

範本是 `src/cmuh_common/roster/`（model / rules / solve / service / storage / ui / export），
已經是這個 repo 自己驗證過的分層形狀。

---

## 現況（2026-07-31 實測，非估計）

| 指標 | 數字 |
| --- | --- |
| main.py 行數 | **16,846**（第一刀前 17,519、第一刀後 17,088） |
| 其中頂層 def/class | 15,640 行（第一刀當時） |
| **`AutomationApp` 一個類別** | **7,530 行（45%）** |
| 還沒搬的「不碰模組級全域」葉子函式 | **38 個 / 668 行**（第二刀前 45 個 / 740 行） |
| `global` 宣告 | 24 個名稱 / 27 處 |
| main.py 覆蓋率 | 約 16% |

量測腳本的作法：用 AST 找出每個頂層函式引用到的**模組級全域**數量。
引用數 0 的就是「可以直接搬走的葉子」；引用數愈高愈晚搬。
（`check_appointment_count` 441 行、引用 **42 個**全域，是耦合最重的單一函式。）

---

## ★鐵律：每一刀都要帶測試★

分層會把行數從 `entrypoints` 層搬到 `shared` 層，而 `coverage_floors.json` 的
`shared` 門檻只有約 1 個百分點的餘裕。**搬一批沒測試的程式碼進 shared，門檻會（正確地）
把它擋下來。**

第一刀實測：那 15 個函式在 main.py 裡只有 **17.9%** 的語句被覆蓋到；
直接搬過去會讓 shared 從 72.5% 掉到 71.4%（低於門檻）。補了測試（88.8%）之後
反而升到 74.2%。

這不是額外的負擔，這是分層的**理由**：搬到獨立模組才測得到。

## 刀法

### ✅ 第一刀（2026-07-31 完成）：HIS 視窗／控制項 Win32 原語

`src/cmuh_common/his_window.py`，15 個函式、427 行。
`tests/test_his_window_2026_07_31.py` 48 支。

選它先做的理由不是行數，是**風險**：這一層正是本 repo 反覆出事的地方
（`IsWindow` vs `IsWindowVisible`、同 class 對話框誤判、殘留舊視窗），
而它在 main.py 裡時判斷邏輯**一行測試都沒有**。集中之後才有一個地方可以加固。

作法（後續每一刀照抄）：
1. 函式原文＋註解**一字不刪**搬過去（註解裡的 `[日期 來源]` 都是踩過的坑）。
2. 加測試接縫：`_user32()` / `_kernel32()` / `_imm32()` 取得器取代散落的
   `ctypes.windll.user32`。**這是唯一的行為面改動**，呼叫的 API、順序、回傳語意照舊。
3. main.py 用 `from ... import 新名 as 舊私有名` —— **只搬家、不改呼叫端**
   （內部 100+ 個呼叫點、tests/ 多支直接用 `main._find_window_...`）。
4. 補測試到覆蓋率不退步為止；跑 `check_coverage.py --update` 把欄杆提上來。

### ✅ 第二刀（2026-07-31 完成）：剩下的 Win32 葉子

併進 `his_window.py`，**14 個函式、216 行**（模組 340 → 767 行）。
測試同檔 +28 支（76 支），沿用第一刀的 `FakeUser32`（補了 `EnumWindows` /
`WindowFromPoint` / `SendMessageTimeoutW` / `IsIconic`+`ShowWindow`）。

`_get_window_pid` `_get_class_name_of` `_get_window_text` `_send_key_to_window`
`_send_message_timeout_ex` `_close_window` `_screen_point_in_window`
`_get_ime_focus_hwnd` `_click_button_by_text` `_click_control_center`
`_click_button_normalized_text` `_ensure_hospital_foreground`
`_scan_unknown_popups` `_send_yiling_menu_command`

★**`_dismiss_status_driver_alert` 刻意不搬**★：它是 **Selenium**（打卡頁的 JS alert），
不是 Win32。原本的清單把它列進來是分類錯誤 —— 放進 `his_window.py` 會是錯的分層。
留在 main.py，等未來的「打卡／Selenium」那一刀（有測試釘住它沒被搬進來）。

搬完連帶：
* `_window_is_ancestor` 不再由 main.py 匯入 —— 它在 main.py 的唯一呼叫端
  （`_screen_point_in_window`）也搬走了，那個呼叫變成模組內部的。
* `tests/test_p2_batch_2026_07_26.py` 的一支守衛跟著改（比對的呼叫名從
  `_post_click_to_control` 變成模組內的 `post_click_to_control`），守的性質沒變。

★這一刀要先處理全域★ 那 42 個全域多半是設定與快取。建議先把它們收斂成一個
明確的 context 物件（roster 的 `ctx` 是現成範例），再搬。**不要**在還靠全域的狀態下硬搬。

### 第五刀（最大、最後）：`AutomationApp` 7,530 行

按既有的方法邊界切：
* `_create_*_tab`（settings / other_programs / abbrev …）→ UI 組裝
* `_update_clinic_lights_loop`(597) / `_update_grid_data`(416) / `process_ui_queue`(160)
  → 資料迴圈
* `start_background_tasks`(298) / `run_subsystem_in_thread`(174) / `setup_hotkeys`(214)
  → 生命週期

★這一刀之前不要動它★ Tk 物件的建立順序、`self.` 狀態的共享範圍都很脆弱，
而 UI 層的測試成本最高（conftest 只有一個全 session 共用的 Tk root，見那裡的說明）。
前四刀做完之後 main.py 大約會剩 15,000 行，屆時再評估這一刀值不值得。
