# 皮膚科程式第一期：現行架構、驗收與後續方向

本頁以已通過正式 CI 的 `2026.09.23.2`（`115ebf7`）為基準，描述本期修改後的實作。舊的《排班程式設計文件》記錄歷史決策與當時設計；若其貪婪排班、只有 PGY／Clerk、同步求解等描述與本頁不同，以執行中的程式及本頁的驗收入口為準。這是工程索引，不是醫療決策規則的變更授權。

## 本期排班規則的可查核解釋

PGY 每半日先滿足照光及治療室必要席位；週三下午只有照光。請假、鎖定及已定案資料先於自動跟診。兩名 PGY 的既有特別安排與手動照光減量仍由原求解規則處理；負數偏移表示實際照光及總工作量減少，報告的公平參考值不能把減量補回。跟診席位沿用 Clerk、家醫、外訓、PGY 的現行優先順序，並遵守每診容量與醫師多元性。

Clerk 以兩週 course 檢視 9–11 診、切片 1–2 次；跨月 course 的可參與半日時段跨兩個月計算。課程尚未走到本月月底時，偏少的跟診／切片只顯示進度，暫不列「已確認缺口」或標紅。家醫與外訓以可參與皮膚科工作的半日（扣請假）計算跟診最低／目標／上限 30%／50%／70%，即使當時沒有門診也保留在分母。家醫勾選的半日是「可參與」，不是必排。報告列出每人每週跟診、已知門診醫師及未知醫師次數；未知醫師不被臆測成多元性。

`day_explanation.py` 的「已確認缺口」只比較實際班表與已知需求／目標，不推斷缺口原因。求解逾時、被取消、局部無改善、硬限制不可行、已證明全域最佳是不同結論。若有請假、停診、容量或鎖定，僅能列為可能限制，不能沒有證據就斷言為根因。

在 repo 根目錄執行；測試只用合成班表、fake HIS／SMTP／portal、暫存目錄，不能連真系統。

```powershell

ruff check src scripts tests

python -m pytest -q
```

關鍵行為的測試分布：主程式熱鍵看 `test_hotkey_registration_transaction_2026_09_03.py`，刷新世代看 `test_main_refresh_generation_2026_09_23.py`；會診查詢／寄送決策看 `test_consult_decision_logic.py`，去識別看 `test_consult_privacy_2026_09_21.py`；打卡官方回讀與錯誤分類看 `test_autoclock_clock_safety.py`、`test_clock_click_confirmation_2026_09_23.py`、`test_autoclock_missed_warning.py`；排班的跨月、半日請假、必要工作、公平／容量與多電腦衝突分別見 `test_roster_course_horizon_2026_08_24.py`、`test_roster_course_spread_2026_09_08.py`、`test_roster_family_2026_09_07.py`、`test_roster_external_course_2026_09_07.py`、`test_roster_stale_overwrite_2026_08_19.py`。歷史 AST 規約測試仍保留，但本期新增測試直接執行 callback、服務、假 portal 與檔案輸出。

效能腳本內含 2／4 PGY、兩梯 4／5 Clerk、0／1／2 家醫或外訓的代表案例，以及半日請假、鎖定、停診與跨月。輸出環境、原始程式版本、輸入 fingerprint、各階段時間與 CP-SAT 狀態、硬限制與品質欄位；暖機不算在五個正式樣本。解讀時比較同一案例的中位數及完整範圍，並先比對求解狀態與品質，不能將較快但品質較差的結果當改善。五個樣本不足以可靠估算 p95。

2026-09-23 本機對照：乾淨的正式 `main` `115ebf7` 與本期隔離工作樹使用同一基準腳本；Windows 11、Python 3.13.1、16 邏輯 CPU、OR-Tools 9.15.6755、`PYTHONHASHSEED=0`，每案暖機一次、正式五次。四案兩端輸入 fingerprint 相同；逐樣本的求解狀態、腳本所列硬限制問題（均為 0）、PGY 工作次數及訓練警告相同。候選測量時修改尚未提交，腳本的 Git revision 仍顯示其父提交 `115ebf7`，實際來源是隔離工作樹；發佈版須另以候選 SHA／CI 核對。數字是腳本調用求解器的耗時，**不含 Tk 回應時間，也不是醫院電腦實測**。

本期沒有採納求解器調參或宣稱求解速度改善。真正已驗證的改善是日排班從 Tk 同步工作改為背景工作：假慢求解器測試確認畫面立即回應、重複按鈕不重入、取消立即顯示且舊結果不套用；假原生求解器同時覆蓋搜尋中及搜尋剛開始前取消，確認 `stop_search()` 會持續傳到該次 CP-SAT 結束。手動排班啟動不依賴 OR-Tools；第一次按自動排班時才在主執行緒檢查或安裝相依套件，失敗仍可手動排班。安裝耗時不計入求解的 180 秒限制；醫院電腦仍需以實機量測確認此限制不會截斷可行的排班。

醫院實機待驗：在沒有患者資料的診間空檔，被動記錄點排班到預覽的耗時、取消回饋與背景工作實際停止時間、CPU／記憶體診斷包；另用使用者操作確認 F7／F8／F12、會診與打卡流程。不得以本機合成資料宣稱醫院電腦效能已改善，也不調整 HIS 保活頻率或打卡時間窗。
